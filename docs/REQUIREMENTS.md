# 食品安全知识库系统 · 需求基线

> 来源：`RAG项目场景模板库-V1.0 / ① RAG场景-EduRAG-V7.5 / 1.47-食品安全知识库系统.html`
> 状态：已解析并作为本项目开发基线与验收依据
> 项目名：FoodSafe 食安通 · 食品安全知识库系统（企业级 RAG 问答平台）

---

## 一、业务目标

某连锁餐饮集团（全国 320+ 直营门店、员工 12000+、年营收 45 亿）涉及原料采购、冷链运输、中央厨房加工、门店出品全链条，需执行食品安全法规与 GB 国标（GB 2760/2762/2763/14881/31654 等）超 1400 项。

| 编号 | 目标 | 量化指向 |
|------|------|----------|
| G1 | 把分散的法规、SOP、案例、营养、供应商知识整合为统一智能问答平台 | 5 大知识库统一入口 |
| G2 | 解决人工查询低效：翻 200-300 页 SOP 手册、耗时 15-30 分钟 | 查询响应降至秒级 |
| G3 | 支持一线口语化提问（"这批鸡胸肉到货温度 8℃ 还能用吗"）命中条款 | 非关键词匹配 |
| G4 | 保证法规引用为**现行有效版本**，避免引用已废止标准被处罚 | 引用可追溯、版本正确 |
| G5 | 事故处置场景秒级定位法规依据与处置流程 | 事故响应从小时级到分钟级 |

## 二、用户角色

| 角色 | 核心诉求 |
|------|----------|
| 餐饮企业品控部门 | 供应商审核、原料验收标准、门店合规检查依据 |
| 门店管理人员（店长/厨师长） | 快速查 SOP 操作规范、处理顾客食品安全投诉 |
| 食品安全管理员 | 随时查阅最新法规、标准与操作指南 |
| 一线操作人员（后厨/配餐/仓管） | 操作中实时获取温度控制、交叉污染防护、个人卫生指导 |
| 卫生监督人员 | 快速定位法规依据进行执法 |

规模：覆盖约 12800 人 · DAU 3500 · MAU 9000 · 峰值并发 350（午餐 11-13 点、晚餐 17-19 点为咨询高峰）。

## 三、核心流程

### 离线数据处理

```
原始文档(法规/SOP/案例/营养/供应商/FAQ)
  → 文档加载（按格式选择加载器）
  → 语义切分（按文档结构：条款层级 / 操作步骤 / 事件结构 / 主题 / 问答对）
  → 向量化（BGE-M3：稠密 1024 维 + 稀疏向量）
  → 存入向量库（Milvus，携带法规编号、适用岗位等元数据）
```

### 离线数据集构建（面向模型训练）

```
知识库原文(data/*.md)
  → 数据预处理（按知识库类型解析：FAQ 拆问答对 / 文档拆标题-正文段）
  → 构建数据集
     ├── 意图分类数据集（6 类意图，train/eval 按哈希独立切分）
     ├── 重排数据集（query / positive / hard negative 三元组）
     └── 指令微调数据集（instruction / input / output，output 摘自原文）
  → 划分训练集 / 验证集（评估集不与训练集重叠）
```

实现位置：`build_dataset.py`（入口）+ `core/dataset_builder.py`（构建逻辑）。
产物：`data/dataset/{intent,rerank,sft}/`。

### 在线查询应答

```
用户提问
  → 问候语检测（简单寒暄直接返回，不做检索）
  → 形态判断 + 意图识别（规则或微调分类模型）
  → 检索（稠密 + 稀疏混合召回）
  → Rerank 重排（选出最相关 Top-K 块）
  → 提示词组装（检索上下文 + 对话历史 + 用户问题）
  → LLM 生成答案（强制标注法规编号版本）
  → 返回答案 + 引用来源
```

### 检索策略（场景文档明确的 4 种，本项目已全部实现）

| 策略 | 适用场景 | 实现位置 | 场景文档给出的效果 |
|------|----------|----------|--------------------|
| 直接检索 | 标准、明确的问题 | `_retrieve_direct` | 基线策略 |
| HyDE | 口语化、模糊提问（"这肉看着有点怪还能用吗"） | `_retrieve_with_hyde` | Recall@10 提升约 22% |
| SubQuery | 复合问题（"开火锅店要满足哪些食品安全条件"） | `_retrieve_with_subqueries` | 拆解子问题分别检索再合并 |
| Backtrack | 检索分数不足时的自救重检索（紧急事故类尤其受益） | `_maybe_backtrack` | 本 MVP 已实现 |

> ⚠️ 口径修正记录：早期版本文档写的是"本项目实现 3 种"（Backtrack 未做）。
> 实际上 `_maybe_backtrack` 早已落地并通过 `[backtrack]` 配置段控制，
> 由 `verify_rag_enhance.py` 覆盖回归。本文档已更正为 4 种。

### 缓存分层（场景文档提及，本 MVP 未引入）

Redis（操作类 TTL=12h / 法规类 24h）→ MySQL FAQ 索引 → BM25 全文检索。
**本项目未实现**：属于「不引入场景文档未要求的额外功能」约束下的取舍（详见下文「范围界定」）。

## 四、知识数据来源

| 知识库 | 内容 | 场景规模 | 格式 | 分块方式 |
|--------|------|----------|------|----------|
| 法规标准库 | 食品安全法、GB 2760/2762/2763/14881/31654、地方条例 | 1500+ 篇 | PDF/MD | 按条款层级（条/款/项），保留法规编号、生效日期 |
| SOP 规范库 | 原料验收、冷链、加工、留样、消毒、卫生等 20+ 关键控制点 | 1200+ 篇 | Word/MD | 按操作步骤，保留 SOP 编号、适用岗位、CCP 标记 |
| 事故处置案例库 | 食物中毒、异物投诉、过敏原事故调查报告 | 800+ 篇 | PDF/MD | 按事件结构（概述/原因/处置/教训） |
| 营养学知识库 | 膳食指南、营养成分、特殊膳食、过敏原 | 1000+ 篇 | MD | 按主题 |
| 供应商资质库 | 供应商审核标准、原料验收标准、冷链要求 | 1500+ 篇 | Excel/MD | 按模块/条款 |
| FAQ 问答库 | 高频咨询问答对 | 2500+ 条 | JSON/MD | 按问答对（Q/A），**以 Q 为唯一分隔符**，保证 Q+A 同块（见下方说明） |

> **FAQ 分块要点（实测踩坑修正）**：FAQ 必须**按 Q/A 整体**分块，不能把 `A:` 也当分隔符。
> 若把 `\nA[:：]` 也列进分隔符，一问一答会被劈成"只有问题"和"只有答案"两块，
> 检索命中问题壳时拿不到答案正文，rerank 分数异常低（实测 0.0151，正常应在 0.7+），
> 同时产生大量 `"Q:"` 两字符垃圾碎片占满召回名额。
> 另外 FAQ 子块需放大到 512（`CHILD_CHUNK_SIZE_OVERRIDE`）——
> 默认 `chunk_size=120` 小于一个完整问答对的长度（约 200 字），仍会二次切碎。
> 修正后单库子块数由 44 → 8，且 8 块全部 Q/A 完整。

来源渠道：国家市场监督管理总局、卫健委、各省市市场监管局官网；企业内部 SOP 与品控规范；疾控中心与监管处罚案例。

## 五、检索与生成要求

### 检索要求

1. **分块**：不同类型文档采用差异化分块策略，块保留来源元数据（法规编号、条款层级、生效日期、适用范围；SOP 编号、适用岗位、CCP 类型；案例事件类型、致病因子、年份）。
2. **混合检索**：稠密语义检索 + 稀疏关键词检索，加权融合。
3. **重排**：初检索结果经 Reranker 二次排序，提升 Top-K 精度。
4. **元数据过滤**：支持按知识库、生效日期、适用岗位过滤（如"2023 年以后的案例"先过滤再检索）。
5. **专业术语适配**：Embedding 模型需能准确编码法规编号、化学名词（苯甲酸钠、亚硝酸盐）、微生物名（沙门氏菌、金黄色葡萄球菌）。

### 生成要求

1. **只基于检索内容作答**，限制模型幻觉。
2. **强制标注法规依据**：引用时必须注明标准编号与版本（"根据 GB 2760-2014 表 1 规定"）。
3. **口语化问题需还原意图**：先明确对应专业判定标准再作答。
4. **信息不足必须拒答**：不得用常识推测，需给出咨询热线。
5. **步骤化输出**：处置类问题给出可执行编号步骤。
6. **缺关键数值必须拒答**（本项目新增的防幻觉硬约束）：当用户追问具体数值（存放天数、用量克数、温度/限量值等）而检索结果中无该数值时，必须直接拒答，严禁用"一般/通常/建议不超过"给出估算范围，也严禁拿语义相近条款凑答案（如把"熟食常温存放 2 小时"套用到"熟鸡蛋冷藏存放天数"）。

## 六、验收要点

| 编号 | 验收项 | 判定方式 |
|------|--------|----------|
| AC-01 | 自然语言提问（含口语化）能返回精准法规条款 / SOP 步骤 / 处置方案 | 用场景文档中的典型问句实测 |
| AC-02 | 答案中包含法规标准编号与版本 | 检查回答文本 |
| AC-03 | 复合问题、口语化模糊问题可正确召回 | 对比直接检索与 HyDE/SubQuery |
| AC-04 | 知识库无相关内容时明确拒答，不编造 | 提问库外问题验证 |
| AC-07 | 追问具体数值但库中无该数值时，明确拒答而非给估算范围 | 提问"熟鸡蛋放几天不能吃"等库内无天数的问题验证 |
| AC-05 | 知识可增量入库且查询即时生效 | 新增文档后重新构建，立即能检索到 |
| AC-06 | 端到端问答可运行且响应为秒级 | 观察耗时输出 |
| AC-08 | 库内问题不被误拒（rerank 分数正常，如 0.7+ 应正常作答） | 提问"冰箱冷藏温度标准是多少"验证，不出现异常低分拒答 |
| AC-09 | 训练数据集可从知识库一键构建，且格式适配训练函数 | 运行 `python build_dataset.py`，检查三类数据集的 JSONL 字段与 train/eval 划分 |
| AC-10 | 意图分类模型缺失时系统仍可正常运行 | 确认 `models/intent-classifier/` 不存在时问答链路正常，日志提示降级为规则分类器 |

### 场景文档给出的基准问句（作为验收测试集）

1. 这批鸡胸肉到货温度 8℃ 还能不能用？应该怎么处理？
2. 冰箱冷藏温度标准是多少？冷冻呢？
3. 食品留样应该留多少克？留多长时间？
4. 顾客说吃了肚子疼，餐厅应该怎么处理？
5. 开火锅店需要满足哪些食品安全条件？
6. GB 2760 对苯甲酸钠在碳酸饮料中的最大使用量是多少？
7. 这个肉看起来有点怪，还能用吗？

## 七、范围界定（本项目做了什么 / 没做什么）

### 已实现（对应需求基线的核心闭环）

- ✅ 多源知识文档导入与结构化切分（6 类知识库、差异化分块策略）
- ✅ BGE-M3 稠密 + 稀疏向量化，Milvus 统一集合存储（元数据区分知识库）
- ✅ 混合检索 + BGE-Reranker 重排 + 元数据过滤
- ✅ 三种检索策略（直接 / HyDE / SubQuery）与策略路由
- ✅ 意图识别链路：6 类意图分类（模型优先，缺失自动回退规则）+ 意图驱动策略路由
- ✅ 训练数据集构建：意图分类 / 重排 / 指令微调三类数据（`build_dataset.py`）
- ✅ 提示词组装、强制法规引用、阈值拒答 + 提示词硬约束双层防线
- ✅ LLM 流式回答 + 引用来源回显
- ✅ FastAPI 接口（HTTP + WebSocket）+ 命令行验证入口 + Web 问答页面
- ✅ **多用户内容隔离（需求 4.2）**：chunk 级 `access_level` / `department` / `visible_to` 三字段 + Milvus 行级过滤 + 出口白名单二次校验 + 缓存键按角色隔离（`core/access_control.py`，回归见 `scripts/verify_access_control.py`）
- ✅ **多格式文档加载器**：PDF / Word / Excel / CSV / JSON / Markdown，按「首选 → 轻量替代 → 零依赖兜底」组织降级链（`core/loaders.py`）
- ✅ **知识库增量更新**：内容哈希 + 清单文件比对，只重算变化的文件，并删除失效文档的旧向量（`core/incremental.py` + `build_kb.py --incremental`）
- ✅ **部署产物**：`Dockerfile` + `docs/deploy/docker-compose.yml`（应用 + Milvus + Redis 一键编排）

### 明确未实现（场景文档中为「可选」或非 MVP 必需）

| 未实现项 | 原因 |
|----------|------|
| 三级缓存的 MySQL + BM25 两级 | 场景文档标注为二期内容；MVP 阶段引入需额外中间件，ROI 不足。**Redis 一级（L2）与进程内一级（L1）已实现**，且缓存键已按「知识库 + 策略 + 权限上下文」三维隔离 |
| LoRA 微调（Qwen2.5-14B） | 场景文档标注为「可选」，需 A100 与标注数据。**本项目已备好训练数据集**，训练与部署由使用者按需进行 |
| 6 类意图分类模型训练 | 场景文档为 Fine-tuned Qwen2.5-7B。**本项目已备好数据集与推理链路**，默认用轻量规则分类，避免引入训练成本；训练好模型放入 `models/intent-classifier/` 即自动接管 |
| vLLM 部署、多模态 RAG、Graph RAG、Agent 化 | 场景文档标注为可选或 2025/2026 前沿方向 |
| MySQL / Redis 会话持久化 | MVP 用进程内会话字典，满足多轮对话验证即可 |

> 取舍原则：遵循「不引入场景文档未要求的额外功能，不做过度抽象与冗余封装」。
